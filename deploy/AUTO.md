# AUTO MON · Усі активні Binance USDⓈ-M · пошук імпульсів із WebSocket

## Ізоляція
Окремий третій бот у `/home/ubuntu/auto` (гілка `feature/auto-h00k-top10-binance-paper`).
Контейнер `auto-mon`, дані `auto_mon_data`, локальний порт `127.0.0.1:3027`,
наявний Caddy `auto.h00k.top`. Жодних змін коду або API сайту `h00k.top`,
`evgen-mon` та `krystian-mon`.

## Ринок і алгоритм
1. Один публічний USDⓈ-M `!ticker@arr` WebSocket відстежує всі активні
   Binance USDT perpetual, список `exchangeInfo` перевіряється раз на годину.
2. При русі >=0,55% від ціни 15–30 секунд тому формується кандидат.
3. **Тільки для кандидатів** другий WebSocket `/market/stream` підписується
   на `{symbol}@kline_1m`. Ліміт 32 активні свічкові потоки. Команди
   підписки й відписки згруповані в пакети (~1,25 повідомлення/с).
4. Потрібні щонайменше 20 послідовних попередніх 1m свічок + поточна.
   При наявності REST-бюджету одноразово завантажується 31 свічка тільки для
   певної монети (не частіше 1 запиту за 15 секунд **для всього auto-mon** (до чотирьох запитів/хв, по одній одиниці ваги за 31 свічку)).
   Коли Binance REST обмежений, бот **не вигадує історію**: накопичує справжні
   WS-свічки приблизно 20 хвилин, поки символ залишається підписаний.
5. Подальші підтвердження цієї монети йдуть без повторних REST-запитів:
   поточна 1m свічка рухається >=0,8%, обсяг у темпі >=2,5x середнього
   за 20 попередніх хвилин, пробій діапазону за 20 хв, напрямок має збігатися
   з імпульсом 15–30 с. Сигнал виникає **до закриття свічки**, тому можливий відкат.
6. Якщо WebSocket замовк, перезапускається і скидає неповну історію; нові
   входи блокуються до відновлення свіжого ринку. Усі сигнали й ордери
   залишаються **тільки в paper-режимі**.

## Захист навантаження
- Не відкривати по одному WS для кожного із ~480 символів.
- Жодних REST-свічок під час кожної перевірки — тільки поодинокий,
  обмежений у часі стартовий прогрів кандидата, якщо ліміт IP дозволяє.
- Захищений початковий прогрів виконується тільки поки остання виміряна вага спільної IP нижча за 1000, залишаючи щонайменше 150 одиниць запасу до внутрішнього порогу auto-mon 1200.
- Не збільшувати `BINANCE_WEIGHT_BUDGET` для обходу загального ліміту IP.
- Враховувати, що інші контейнери VPS використовують ту саму зовнішню IP.
- Панель показує WS кандидати, перевірки, кількість прогрітих символів та
  одноразові REST-завантаження.
- Ця зміна стосується тільки пошуку імпульсів. Paper-модель виконання
  може робити окремі REST-запити стакана й контрактного стану при входах/виходах.

## Тестова торгівля
За відсутності перевірених ключів Binance працює публічна 1x paper-модель
на реальних котируваннях з орієнтовною комісією; ліквідація не моделюється.
**Реальні ордери заборонені** і тестнет не використовується.

## Оновлення VPS
```sh
cd /home/ubuntu/auto
sudo -u ubuntu git pull --ff-only origin feature/auto-h00k-top10-binance-paper
docker compose -f deploy/auto.compose.yaml build auto-mon
docker compose -f deploy/auto.compose.yaml up -d --no-deps --force-recreate auto-mon
curl -fsS https://auto.h00k.top/healthz
```
**Не використовуйте `down -v`: це видалить тестову історію.**

## Зворотні тестові входи (2026-11-09)
У режимі AUTO (`AUTO_IMPULSE_ALL=true`) підтверджений імпульс LONG → нова SHORT paper-позиція, імпульс SHORT → LONG paper. Сервіс примусово застосовує `reverseEnabled:true` незалежно від збережених старих налаштувань; це діє і для ручного входу із сигналу. TP/SL розраховуються для напрямку фактичного виконання. Старі відкриті позиції та історія не змінюються, сигнал зберігає справжній напрямок руху. Інші боти та `mon/main` не зачіпаються. Не гарантує прибутковості.
