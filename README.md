# Evgen trading terminal

Приватний термінал для одного власника: сканер технічних формацій, віртуальна торгівля на реальних котируваннях і окремий режим реальних ордерів Binance / Bybit.

## Що реалізовано

- Серверні позиції, історія, інтервали входів і тайм-стоп; закриття вкладки не зупиняє двигун.
- Два розділені рахунки: paper / live. У віртуальному режимі немає торгових запитів до приватного API.
- Активні **USDT perpetual** контракти вибраної біржі, включно з пагінацією Bybit. Spot, USDC та inverse контракти не входять у цей набір.
- 11 реалізованих детекторів: Double Top / Bottom, H&S / Inverse H&S, Ascending / Descending / Symmetric Triangle, Rising / Falling Wedge, Bull / Bear Flag. Це підтримуваний набір, а не всі можливі фігури технічного аналізу. Детектори можуть помилятися; їхню якість потрібно оцінювати окремо.
- Черга всіх контрактів і вибраних таймфреймів, закриті свічки, кешування котирувань, обмеження частоти, пауза після 429. Відсутність патернів повертає порожній результат.
- Пароль із scrypt, серверні сесії, HttpOnly / SameSite cookie, перевірки Origin та CSRF, обмеження спроб входу.
- API-ключі у SQLite шифруються AES-256-GCM. Ключ шифрування розміщено окремо в конфігурації сервера. API повертає лише статус підключення.
- Реальні ордери через CCXT, One-way Mode, точність інструмента, TP/SL на біржі, reduce-only закриття, збережений намір до надсилання, відсутність сліпих повторів після timeout. Закриття звіряється зі станом біржі та історією виконань.
- Окремий захищений endpoint для cron-job.org. Читання панелі не запускає сканування.

Це одна приватна інсталяція з одним адміністратором. Публічної реєстрації та ізоляції кількох користувачів немає.

## Локальний запуск

Потрібен оновлений Node.js **24 LTS, 24.22.1 або новіший**. Пакети встановлюються через npm та package-lock.json. Перевірено на Node.js 24.22.1; для мережевої залежності CCXT зафіксовано виправлену undici 7.30.1.

```bash
npm ci
npm run password
```

Створіть `.env` на основі `.env.example`, задайте отриманий ADMIN_PASSWORD_HASH, випадкові ENCRYPTION_KEY та CRON_SECRET. Для локальної розробки використовуйте `APP_ORIGIN=http://127.0.0.1:3010`, `DATA_DIR=./data`.

```bash
npm run dev
```

Production:

```bash
npm run typecheck
npm test
npm run build
npm start
```

Не запускайте `npm run dev` на публічному VPS. Production-сервер не завантажує Vite. CCXT завантажує тільки адаптер вибраної біржі при першому приватному API-запиті.

## Перенесення на OVHcloud VPS

### Варіант із наявним Docker і Caddy

На перевіреному VPS `hook.vps.ovh.net` уже є Docker і Caddy, тому можна встановити застосунок без зміни системного Node.js:

```bash
sudo bash deploy/install-docker.sh
```

Для оновлення наявної інсталяції, зокрема після локальних правок у `src/App.tsx`:

```bash
cd /home/ubuntu/h00k/h00k/evgen-mon &&
git fetch origin codex/ovh-trading-terminal-20261025 &&
mon_updater=$(mktemp) &&
git show FETCH_HEAD:deploy/update-docker.sh > "$mon_updater" &&
sudo bash "$mon_updater" "$PWD"
```

Оновлювач перевіряє гілку й можливість fast-forward, залишає приватну резервну копію App, diff та індексу в `/tmp/evgen-mon-update.*`, зберігає локальний App у stash й переносить сумісні правки на нову версію. У конфліктних ділянках App пріоритет має оновлений код; попередній файл, сторони конфлікту та оригінальний stash зберігаються. Підтримано також незавершений конфлікт App після `git stash apply`. За конфліктів в інших файлах, незавершеного merge/rebase або розходження локальних комітів скрипт зупиняється. Потім звичайний інсталятор виконує тести, збірку та health-перевірку. Для підготовки файлів без збірки є другий аргумент `--prepare-only`.

Інсталятор збирає офіційний Node 24 LTS образ, виконує перевірку типів, тести та production-збірку, пропонує створити пароль і запускає окремий контейнер `evgen-mon` на `127.0.0.1:3010` з лімітами 768 МБ RAM і 0,5 CPU. Дані розміщено в `/var/lib/evgen-mon`, конфігурацію — у `/etc/evgen-mon.env`. До чинного Caddyfile додається лише virtual host `evgen.h00k.top`, зі збереженням резервної копії та перевіркою перед reload. Чинні контейнер і virtual host h00k.top не змінюються. DNS інсталятор не редагує.

Для цього VPS запис `A` піддомену `evgen` має вказувати на `57.129.171.244`. Старе перенаправлення OVH використовує `213.186.33.5`; змініть лише запис `evgen`, не записи головного домену. Якщо DNS оновлено вже після встановлення, перевірте його розповсюдження та виконайте `sudo systemctl reload caddy`.

```bash
sudo docker ps --filter name=evgen-mon
sudo docker logs --tail 50 evgen-mon
curl --fail http://127.0.0.1:3010/healthz
```

### Варіант із systemd та Node.js на хості

Інсталяцію розраховано на Linux із systemd, зокрема Ubuntu / Debian. Потрібен саме VPS / dedicated server із Node.js, а не тариф спільного PHP-хостингу OVH. Перед перенесенням перевірте поточні CPU/RAM, reverse proxy та резервну копію чинного h00k.top.

1. На VPS встановіть Node.js 24 LTS із офіційного джерела та Git. Отримайте перевірену гілку репозиторію.
2. Із кореня проєкту запустіть `sudo bash deploy/install.sh`. Інсталятор створює окремого системного користувача `evgen-mon`, каталог релізів `/opt/evgen-mon`, базу `/var/lib/evgen-mon` та `/etc/evgen-mon.env`. Новий пароль вводиться приховано. При наступному запуску конфігурація та дані зберігаються.
3. У DNS-зоні **h00k.top** додайте `A` для піддомену `evgen` на публічний IPv4 VPS. `AAAA` додавайте лише для налаштованого IPv6 цього VPS. Записи головного домену не змінюйте.
4. Додайте окремий HTTPS virtual host до наявного reverse proxy. Для Caddy використайте `deploy/evgen.caddy`, перевірте `caddy validate --config /etc/caddy/Caddyfile` та перезавантажте Caddy. Для Nginx є альтернативний `deploy/evgen.nginx.conf`; перевірте `nginx -t`, отримайте сертифікат `certbot --nginx -d evgen.h00k.top` і перезавантажте Nginx. Не встановлюйте другий proxy поверх уже зайнятих портів 80/443 і не замінюйте конфігурацію h00k.top.
5. Перевірте `https://evgen.h00k.top/healthz`, вхід і віртуальний режим. Порт 3010 слухає лише loopback; відкривати його у firewall не потрібно.
6. Налаштуйте cron-job.org за наступним розділом. Увімкніть завдання лише після перевірки HTTPS та секретного заголовка.

Інсталятор не змінює DNS і не редагує чинний reverse proxy автоматично. Якщо новий реліз не проходить локальну health-перевірку, він повертає попередній симлінк релізу.

Сервіс має початкові обмеження `CPUQuota=50%` одного ядра, `MemoryHigh=512M`, `MemoryMax=768M`, нижчий пріоритет CPU та диска. Це ліміти, а не виміряне споживання. Підберіть їх після перевірки характеристик VPS; надто низький ліміт може затримувати сам бот.

```bash
systemctl status evgen-mon
journalctl -u evgen-mon -n 100 --no-pager
systemctl show evgen-mon -p MemoryCurrent -p CPUUsageNSec
```

### Оновлення встановленого термінала

Оновлюйте з того самого каталогу Git, з якого встановлювали застосунок. Перед оновленням перегляньте `git status --short`: збережіть власні правки, особливо якщо змінювали текст сторінки входу безпосередньо на VPS. Не скидайте їх через `git reset --hard`. Для резервної копії даних скористайтеся розділом «Дані, резервні копії та графік».

Для чинної Docker-інсталяції на цьому VPS використовуйте блок оновлювача з розділу вище: він отримує `codex/ovh-trading-terminal-20261025` і зберігає сумісні локальні правки. Ця гілка об’єднує також виправлення `codex/fix-pattern-entry-reverse-20261026` (`db97cd9`), тому встановлений `db97cd9` оновлюється через fast-forward. Якщо Git повідомляє про інше розходження історії, скрипт зупиниться для окремого узгодження комітів.

Використайте інсталятор для чинного способу запуску. Для Docker (контейнер `evgen-mon`):

```bash
sudo bash deploy/install-docker.sh
sudo docker ps --filter name=evgen-mon
sudo docker logs --tail 50 evgen-mon
```

Для systemd (сервіс `evgen-mon.service`):

```bash
sudo bash deploy/install.sh
sudo systemctl status evgen-mon --no-pager
```

Повторний запуск інсталятора перебудовує застосунок і використовує наявні `/etc/evgen-mon.env` та `/var/lib/evgen-mon`. Самого `docker restart` або перезавантаження VPS недостатньо для застосування змін до TypeScript. Обидва інсталятори перевіряють нову збірку та повертають попередній запуск, якщо локальна health-перевірка не проходить.

```bash
curl --fail --show-error http://127.0.0.1:3010/healthz
```

Після оновлення відкрийте термінал, перевірте стан «Автоматичні входи», «Реверс напрямку» та «Лише підтверджені формації», а після редагування натисніть «Зберегти зміни». Дочекайтеся нового пакета cron або запустіть сканування вручну. Після переходу на оцінювання версії 2 старі оцінки виключаються одразу; нові формації з’являються під час нового проходу.

## Години автоматичної торгівлі

У «Налаштування → Стратегія та виконання» є блок «Години автоматичної торгівлі». Увімкніть «Торгувати за розкладом», додайте сесію або власні години, виберіть дні та натисніть «Зберегти зміни». Перемикач «Автоматичні входи» вмикається окремо: сам розклад не запускає торгівлю. За замовчуванням розклад вимкнений, зокрема після оновлення наявної інсталяції.

Крипторинок доступний цілодобово; [офіційна довідка Coinbase](https://help.coinbase.com/en/trading-and-funding/trading-hours-market-closures) пояснює відмінність від біржових сесій акцій. Нижче — редаговані шаблони регіональних часових вікон, а не офіційний календар відкриття Binance / Bybit чи рекомендація щодо прибуткових годин.

| Шаблон | Часовий пояс | Місцеві години | Початково обрані дні |
| --- | --- | --- | --- |
| Азія · Токіо | Asia/Tokyo | 09:00–18:00 | Пн–Пт |
| Європа · Лондон | Europe/London | 08:00–17:00 | Пн–Пт |
| Америка · Нью-Йорк | America/New_York | 08:00–17:00 | Пн–Пт |

Кожне вікно має власні назву, пояс, години та дні; у власному вікні початково вибрано Europe/Warsaw. Вихідні можна додати. Дозволено до 20 вікон; достатньо, щоб одне з них було активним. Система використовує названі часові пояси, тому літній/зимовий час Лондона, Нью-Йорка чи Варшави враховується за їхніми власними правилами, незалежно від UTC на VPS.

Початок включається, кінець не включається. Для нічного вікна дні означають день початку: Пт 22:00–02:00 працює до суботи 02:00, але не в суботу ввечері. Однаковий час початку й завершення означає цілий обраний місцевий календарний день. Це тижневий розклад без календаря державних свят.

Розклад перевіряється на сервері перед автоматичним входом і повторно після асинхронної підготовки ордера. Поза вікнами нові автоматичні входи призупинені та відновлюються самостійно, з урахуванням налаштованого інтервалу входів. Фільтри формацій, Revers і свіжість сигналів залишаються обов'язковими. Сканер продовжує збирати свіжі дані; супровід відкритих позицій, біржові TP/SL, тайм-стоп, звірка ордерів і ручні дії працюють поза розкладом також. Кінець сесії сам по собі не закриває відкриту позицію.

Поточний дозвіл і назви активних вікон видно в панелі. Розклад зберігається в наявній базі та переживає перезапуск контейнера; відкритий браузер для його роботи не потрібний.

## cron-job.org

- URL: `https://evgen.h00k.top/api/cron/scan`
- Метод: **POST**
- Розклад: `* * * * *`, часовий пояс `Europe/Warsaw`
- Заголовки: `Content-Type: application/json` і `Authorization: Bearer <CRON_SECRET із /etc/evgen-mon.env>`
- Тіло: `{}`
- Архівування відповідей: вимкнено.

Endpoint одразу повертає 202 при прийнятті пакета або 200, якщо робота вже виконується / інтервал ще не минув. Нові паралельні сканери не накопичуються. Він не повертає ключі або стан рахунку.

У режимі `external` без увімкненого завдання з правильним `Authorization` регулярних запусків немає. Створене, але вимкнене завдання їх не виконує. Панель відображає час останнього прийнятого cron-виклику, кількість оброблених завдань, знайдених формацій і помилок. Порожній скрінер окремо пояснює відсутність запусків, збій API, прострочений розклад або відсутність відповідностей фільтрам.

Зовнішній cron **не виносить обчислення з VPS**. Він тільки запускає пакет. За замовчуванням: до 200 пар/таймфреймів за пакет і 4 публічні запити за секунду. Наприклад, для 600 пар на одному TF потрібно приблизно три хвилинні виклики плюс мережеві затримки; шість TF збільшують набір до 3600 завдань. Повний ринок не є миттєвим скальпінговим потоком. Панель показує прогрес, останній повний прохід і вік сигналів.

У кожному пакеті таймфрейми чергуються між монетами, щоб старші TF не чекали завершення всіх монет на першому TF. У скрінері формація залишається видимою до закриття наступної свічки свого таймфрейму або до заданого `maxSignalAgeSeconds`, якщо він більший. Ліміт віку **нового торгового входу** залишається точно `maxSignalAgeSeconds`: після його завершення кнопка входу вимикається, а автоматична торгівля пропускає такий сигнал. Старі сигнали не стають дозволеними для торгівлі через довше відображення. Пошук охоплює всі знайдені формації; таблиця показує перші 200 відповідностей, щоб не перевантажувати браузер.

Оцінювання формацій версії 2 використовує обмежену суму **структура 0–60 + пробій 0–25 + обсяг 0–15**. Структура враховує геометрію відносно глибини та волатильності, баланс частин, звуження і похибку ліній залежно від типу. Підтвердження оцінює фактичне закриття за межею, відстань пробою в ATR та положення закриття у свічці. Обсяг порівнюється з попередніми 20 свічками: звичайний 1× дає 5/15, 2× — 15/15, відсутні дані — 0. Без пробою оцінка не перевищує 60. Прапори використовують ці ж складові замість фіксованих 80 балів. Натисніть оцінку в таблиці для її складових. Це евристична оцінка якості, **не відсоток успішних угод**; прибутковість потребує окремої перевірки на історичних даних.

Час підтвердженої формації — перша свічка пробою, а не час чергового сканування. Ідентифікатор прив’язано до структури, тому та сама формація не створює новий торговий сигнал з кожною свічкою. Повернення всередину після пробою або перетин ліній за вершиною трикутника відсіює формацію. Для симетричного трикутника напрям і рівень входу відповідають фактично пробитій межі. TP/SL на графіку формації обчислюються від її рівня входу; виконана угода зберігає власні фактичні рівні. Після оновлення старі оцінки версії 1 виключаються з показу й нових входів, а черга починає новий прохід. Чинні позиції та історія зберігаються.

Реальні позиції звіряються окремим серверним таймером кожні 5 секунд. Paper-позиції супроводжуються потоком цін із перевіркою щосекунди. Інтервал входів і максимальний час позиції налаштовуються незалежно від cron; точність тайм-стопа обмежена цим інтервалом, доступністю API та мережею. Біржові TP/SL не залежать від cron. Потік симулятора підписаний лише на відкриті позиції; для значно швидшого суцільного сканування потрібен окремий потоковий збирач, виміряний за ресурсами.

BINANCE_WEIGHT_BUDGET — абсолютний поріг спільного IP weight, за яким цей сканер робить паузу. Він не резервує ліміт для h00k.top і не координує його запити; обидва застосунки все одно ділять ліміт IP. Внутрішній розклад доступний через `SCHEDULER_MODE=internal`, але не вмикайте обидва планувальники без потреби.

## Реальний режим

Після встановлення режим paper, автоматичні входи вимкнено, `ENABLE_LIVE_TRADING=false`. Перевірка API-ключів виконує лише читання балансу та позицій. У цій роботі реальні біржові ордери не виконувалися; адаптери перевірено підставними відповідями.

Для самостійного запуску реальної торгівлі власник сервера встановлює `ENABLE_LIVE_TRADING=true`, перезапускає сервіс, зберігає ключі в захищених налаштуваннях, перевіряє їх та явно обирає реальний режим. Ключам потрібні читання й торгівля деривативами; дозвіл виведення не потрібен. Підтримується **One-way Mode**. Перемикання біржі/режиму, заміна ключів та зміна плеча блокуються за відкритої або неузгодженої експозиції.

Paper використовує модель виконання з біржовими даними, описану нижче. Реальний P&L враховує отримані виконання, доступні USDT-комісії та funding із приватної історії конкретної біржі. Funding повторно звіряється не раніше ніж через хвилину після закриття; до успішної звірки результат позначено неповним. Біржові ліквідаційні збори поза звичайними виконаннями та комісії в інших валютах поки не включені в реальний торговий P&L. Баланс біржі залишається джерелом стану реального рахунку. Позиції по символах, якими керує бот, не слід паралельно змінювати іншим ботом або вручну: при розбіжності нові входи призупиняються.

### Симулятор виконання та витрат

Нові paper-позиції використовують **isolated-модель**, власне плече, початкову й поточну виділену маржу. Зміни налаштувань не переписують параметри вже відкритої позиції. У paper не надсилаються ордери й не змінюється плече реального акаунта; дозволені лише читання ринку, тарифів і ризику.

- **Комісії:** `paperFeeMode=account` за замовчуванням читає персональний taker-тариф через API; ставки входу та виходу зберігаються окремо. Для входу тариф кешується на 10 хвилин, на виході оновлюється. Потрібні збережені API-ключі з правами читання. `manual` явно застосовує `takerFeePercent`, знімок якого фіксується на вході. Немає прихованої підміни помилки API ручною ставкою. Спеціальні знижки при оплаті іншими токенами можуть відрізнятися від поверненого тарифу.
- **Виконання:** після `paperLatencyMs` (типово 200 мс) читається свіжий стакан до 1000 рівнів. Купівля проходить asks, продаж — bids; обчислюється VWAP всього обсягу. Стакан старший за 2 секунди, некоректні рівні, нестача глибини, мінімальні/максимальні біржові обсяги та перевищення допуску входу блокують нову угоду до використання сигналу. Номінал обмежений заданим бюджетом. На виході допуск входу не заважає аварійному закриттю. Модель повного виконання не вигадує ліквідність і не моделює частково виконаний залишок: якщо видимого обсягу не вистачає, вхід відхиляється, а вихід повторюється зі збереженою причиною.
- **Супровід:** WebSocket передає last/mark лише для відкритих paper-символів. Перший спостережений TP/SL зберігається при швидкому відскоку. Основна перевірка — щосекунди, REST є резервним джерелом; розрив потоку/перезапуск із пропуском спостереження позначається в позиції й історії. Реальна торгівля зберігає п'ятисекундну звірку. Це не відновлення всіх торкань під час відсутності з'єднання.
- **Funding:** використовується опублікована історія ставок і моментів нарахування конкретного контракту. Сума = кількість × mark на момент нарахування × ставка × знак напряму; плюс означає витрату, мінус — надходження. Binance повертає settlement mark. Для Bybit використовується open хвилинної mark-свічки — це окремо позначене наближення. Кошти списуються з вільного гаманця, при його нестачі — із виділеної маржі. Події зберігаються й не застосовуються повторно після перезапуску. Відсутність очікуваної події не вважається нульовим funding.
- **Маржа/ліквідація:** рівні ризику читаються з Binance leverage brackets (потрібен ключ читання) або публічного Bybit risk-limit. Враховуються ставка підтримувальної маржі та відрахування рівня. Bybit додатково включає в початкову й підтримувальну маржу резерв комісії закриття за bankruptcy price; для Binance такого резерву в цій моделі немає. Рівні оновлюються кожні 10 хвилин, невдале оновлення позначається. Поріг перевіряється за mark price, незалежно від last price. Повна ліквідація моделюється як втрата залишку isolated-маржі з окремою позначкою `isolated-bankruptcy-model`; це не звичайне виконання за стаканом і не точне відтворення біржового страхового клірингу. Cross/portfolio margin, часткова ліквідація та ADL не моделюються.
- **Відновлення:** виконання виходу записується до очікування комісій/funding. Якщо API затримує витрати, позиція має стан `closing`: її ціна й час модельного виходу зафіксовані, але остаточний P&L очікує звірки. Повторний цикл/перезапуск не виконує вихід знову за новою ціною. Старі відкриті позиції підключаються до нової моделі з явною позначкою, що їхній історичний вхід не реконструйовано. Старі закриті записи не переписуються.

`netPnl = grossPnl − entryFee − exitFee − fundingCost`. Прослизання вже міститься у фактичних модельних цінах й **не віднімається вдруге**. Баланс paper одразу враховує комісію входу та funding; закриття додає лише валовий результат мінус комісію виходу. CSV містить ставки, джерела, витрати, затримку, знімок маржі, зауваження та журнал нарахувань funding.

Для запуску оновіть контейнер, відкрийте налаштування й перевірте джерело комісії. Для найбільш точної доступної ставки збережіть ключі читання відповідної біржі. Без ключів можна використовувати Bybit із явним ручним тарифом; Binance потребує ключа читання для рівнів маржі навіть при ручному тарифі. Увімкнення реальної торгівлі для цього не потрібне. На точність впливають мережева затримка, невидима ліквідність, неповна історія, зміни тарифів та модель ліквідації. Результат залишається оцінкою, а не гарантією виконання на біржі.

Джерела протоколів: [Binance WebSocket URL migration](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-market-streams/Important-WebSocket-Change-Notice), [Bybit risk limits](https://bybit-exchange.github.io/docs/v5/market/risk-limit), [Bybit funding history](https://bybit-exchange.github.io/docs/v5/market/history-fund-rate), [Bybit funding calculation](https://www.bybit.com/en/help-center/article/Funding-fee-calculation), [Bybit liquidation](https://www.bybit.com/en/help-center/article/UTA-Trading-Rules-Liquidation-Process).

Невідомий результат ордера зберігається як pending. Бот робить запити звірки, але не надсилає той самий вхід повторно. Якщо біржа так і не дає визначити результат, нові входи залишаються заблокованими до ручної перевірки стану. Автоматичного примусового очищення pending немає.

## Дані, резервні копії та графік

Історія та CSV містять час відкриття й закриття, таймфрейм, назву формації, її оцінку 0–100 і підтвердження **на момент входу**. Оцінка та статус беруться зі збереженого сигналу, а не з поточного скрінера. У CSV окремо записано фактичний напрям угоди та початковий напрям сигналу (для Revers), біржу, причину виходу, тип результату та повноту комісій. Експортується вся збережена історія вибраного режиму (до 1000 угод), таблиця показує останні 100. Час CSV — ISO 8601 UTC із суфіксом `Z`; час інтерфейсу — Europe/Warsaw. Файл використовує UTF-8 BOM і роздільник `;` для Excel. Старі закриті угоди без збереженої оцінки або підтвердження мають порожні відповідні поля: ці дані заднім числом не вигадуються. Уже відкриті позиції отримають ці поля при закритті зі свого збереженого сигналу.

SQLite працює в WAL-режимі. Для простої узгодженої резервної копії зупиніть тільки `evgen-mon`, скопіюйте `/var/lib/evgen-mon` разом із `/etc/evgen-mon.env`, потім запустіть сервіс. Без ENCRYPTION_KEY відновлені API-ключі не розшифруються. Не розміщуйте резервні копії у web-root. Сесії та зашифровані ключі входять у базу; доступ має бути обмежений власником сервера.

Залишено наявний **HookChart із mon** — він малює графік у браузері. Тепер він отримує кешовані свічки з вибраної Binance / Bybit; дублювати весь h00k.top або його процеси для цього не потрібно. Альтернативне вбудовування TradingView використовує ту саму вибрану біржу. Окремі нові функції HookChart можна переносити з h00k.top після порівняння версій.

Натискання на назву монети у скрінері, відкритих позиціях або історії відкриває HookChart із блакитним рівнем входу, зеленою ціллю TP та червоним стопом SL. Точка на свічці позначає час і ціну входу. Для історії завантажується вікно з 300 свічок біля входу з біржі угоди; повторне автоматичне опитування такого вікна вимкнено. Таймфрейм і фактичні TP/SL зберігаються при відкритті та закритті нових угод і не змінюються разом із поточними налаштуваннями. Старі записи історії, які не містять TP/SL, показують лише збережений вхід та пояснення про відсутні рівні.
